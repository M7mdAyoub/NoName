# Logic Review of the Plan (pre-build)

Findings from cross-reading `docs/plan/Problem statement and solution.md`, `docs/plan/BACKEND_IMPLEMENTATION_PLAN.md` and the public-frameworks note.
Each item has a **proposed resolution** and the phase that must settle it. The session for that phase confirms or changes the resolution, then records the outcome in `DECISIONS.md` and updates the Status column here.

Status values: `open` | `resolved (phase NN, D-xx)` | `accepted-risk`

Rule: migrations that have not been applied yet may still be amended in the plan. An applied migration is never edited, only superseded by a new one.

| ID | Sev | Phase | Issue | Proposed resolution | Status |
|---|---|---|---|---|---|
| L-01 | High | 00 | SQLAlchemy Core over `sqlite3` uses implicit transaction handling, which fights `BEGIN IMMEDIATE`. Async routes calling a sync driver also block the event loop. | Open connections with `isolation_level=None` (autocommit) and issue explicit `BEGIN IMMEDIATE`/`COMMIT`. Use sync (`def`) route handlers so FastAPI runs them in a threadpool. One connection per request/job. Prove with a concurrency test. | resolved (phase 00, D-02) |
| L-02 | High | 00 | "Hard deletes blocked by triggers on every business table" conflicts with tables that must delete rows: `membership_component` (PUT replaces the set), `indicator_field_link` (rewritten on approval), `qual_coding` (rebuilt on re-analysis), `entity_alias`, token tables, `indicator_dirty`, `job`. | Define an explicit exempt list in the trigger generator: join/derived tables (`membership_component`, `indicator_field_link`, `qual_coding`, `indicator_dirty`), token tables, `job`, `entity_alias`. Every other table with `deleted_at` gets the trigger. CI "no hard DELETE" check uses the same list. | resolved (phase 00, D-03) |
| L-03 | Med | 01 | Org admins have implicit project-admin rights but no `project_membership` row; platform admins also bypass membership. `ProjectScope` resolution is not specified for these. | `ProjectScope` resolves: platform admin, then org admin of the owner org, then project membership. A project the caller cannot see is always 404. Cover all three paths in the role-matrix test. | open |
| L-04 | High | 03 | Client-generated ids (submission, file, entity) plus `ON CONFLICT(id) DO NOTHING`: a user in project B could send an id that exists in project A and receive `duplicate`, which leaks existence and silently drops data. | On conflict, compare `project_id` (and form_version for submissions). Same project = `duplicate`. Different project = reject `id_conflict`. Applies to `/files` and entity ids too. Add a tenancy test. | open |
| L-05 | Med | 03 | `submission.collected_on` is a generated column from the UTC `collected_at`, but periods are in the project's timezone (e.g. Asia/Amman, UTC+3). Evening submissions land on the wrong day and period. | Make `collected_on` a normal `TEXT NOT NULL` column computed by the service from `collected_at` in `project.timezone`. Amend migration 0005 before it is first applied. Add an engine test around midnight. | open |
| L-06 | High | 05 | Indicators belong to a component through their result, but definitions count across the whole project unless they filter by component. A Ramtha indicator could count Sahel Horan records. | Add `scope: "component" \| "project"` to the definition (default `component`). The compiler adds `submission.component_id = indicator's component` by default. Forms with NULL component are shared. Document and test. | open |
| L-07 | Med | 02/06 | `indicator.reporting_frequency` may differ from the project's period grid; behaviour is unspecified. | Project periods use the project frequency. An indicator with a coarser frequency has targets and reported values only on periods ending at its boundary; other periods show `not_due`. Confirm and add a `not_due` handling rule to the dashboard. | open |
| L-08 | Med | 05 | `index` indicators depend on other indicators: no cycle check, no compute order, no status propagation. | Validate the dependency graph is acyclic on approval. Compute in topological order. If any component is not `ok`, the index is `not_computable` with a reason naming it. | open |
| L-09 | Med | 05 | `cumulative` counts "from project start", but `project.start_date` is nullable. | Cumulative start = `project.start_date`, else first reporting period start. Activating a project requires one of them. | open |
| L-10 | Med | 02 | `entity_type.identity_scope = 'organization'` is not supported by the schema: `entity` carries `project_id` and its unique index is per project. Open decision #3 claims both are supported. | v1: only `project` scope; the validator rejects `organization`. Cross-project identity is a later migration (add `organization_id` plus an org-level unique index). Record the decision. | open |
| L-11 | Med | 03/12 | `submission.component_id` is NOT NULL, but `form.component_id` may be NULL (shared form). A public or participant form then has no component to assign. | Public/participant forms must have a non-null `component_id`; enforced at form-version publish. For shared staff forms the collector sends the component. | open |
| L-12 | High | 05 | The engine counts `status <> 'rejected'`, so unreviewed public/participant submissions (status `submitted`) would inflate indicators (applications counted as trainees). | Submissions from forms with `access <> 'staff'` count only once `approved`. Staff submissions count when `submitted`, `flagged` or `approved`. Test it. | open |
| L-13 | Med | 03 | The insert-only audit log stores `before`/`after` JSON, which would copy `pii` field values (e.g. national IDs) permanently. Insert-only also blocks erasure requests. | Audit entries mask `pii` fields (store a hash or `"[pii]"`). Define a `redact` operation that blanks pii inside `submission.data` and its revisions (a soft state, audited), as the only sanctioned erasure path. | open |
| L-14 | Low | 01 | Refresh token in an httpOnly cookie needs CSRF protection on `/auth/refresh` and `/auth/logout`. | `SameSite=Strict`, an Origin check, and a custom-header requirement on those two routes. | open |
| L-15 | High | 08/09 | The phase "done when" criteria assume a running Qwen model, which Claude Code sessions will not have. | Build and test steps against a mock LLM with recorded fixtures. Anything needing the real model becomes a user-run task (`make ai-eval`) with the results pasted into the handoff. A phase is "code complete" without it. | open |
| L-16 | Med | 05/06 | The ENABEL benchmark needs ENABEL files that may not be available or permitted. | Build a synthetic framework and dataset that mimics the ENABEL indicator patterns (distinct people, cumulative, require_in, latest, by sex/age/refugee). Real ENABEL files are optional extras. | open |
| L-17 | Low | 11 | Plan requires locked-period reports to be "byte-identical", which xlsx zips cannot guarantee (timestamps, docProps). | Require content-identical (same cell values and formatting); optionally fix the core properties and zip timestamps. | open |
| L-18 | Med | 12/13 | The public portal (original phase 10) is built after hardening (original phase 9), so the largest attack surface escapes the security review. | Order is now: portal (12), then hardening (13), whose review explicitly covers every `/public` route. | resolved (kit ordering) |

## How sessions use this file
1. At the start, filter for your phase and for `open` items from earlier phases that touch your area.
2. Confirm or change the resolution before coding, and write it as a decision in `DECISIONS.md`.
3. Mark the item `resolved (phase NN, D-xx)`.
4. New problems you discover get the next free `L-xx` id, with the phase that must settle them.
